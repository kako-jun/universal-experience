# ADR: ルーペ窓を唯一の描画単位にする（対象アプリ指定はルーペの自動配置モード）

- **決定日**: 2026-09-26（kako-jun、Issue #44 の決定コメント）
- **記録日**: 2026-09-26（ADR 化）
- **追記日**: 2026-09-28（Issue #81。未決事項の確定・OS ごとの可否）
- **ステータス**: Accepted

## 文脈（問題）

ue のルーペ窓（`lib/services/loupe_window_controller.dart`）は、ユーザーが手で
動かし・大きさを変える「覗き窓」として画面の一部にフィルタを適用する体験を
提供する（#14）。一方で、ユーザー体験としては「特定のアプリのウィンドウにだけ
自動でフィルタをかけたい（対象アプリ指定）」という要望もあり得る。

この 2 つを別々の描画経路（例: 手動ルーペ用のキャプチャ・シェーダ・uniform 経路と、
対象アプリ自動追従用の別経路）として実装するか、単一の経路に統合するかを
決める必要があった。別経路にすると、キャプチャ・シェーダ適用・uniform 同期の
実装をそれぞれ持つことになり、保守対象が二重化する。

## 決定

**両立させる。ただし描画の基本単位はルーペ窓ひとつに統一し、「対象アプリ指定」は
ルーペ窓の自動配置モードとして実装する。**

- **手動モード**: 従来どおり、ユーザーがルーペ窓を動かし、大きさを変える。
- **対象アプリ指定モード**: 選んだアプリのウィンドウに、ルーペ窓の位置と大きさを
  自動で合わせ、対象ウィンドウの移動・リサイズに追従する（最前面・クリックスルーを
  ON にする。手動モードの既定とは異なる）。
- キャプチャ・シェーダ・uniform の経路は 1 本で済む。モードの違いは
  「ルーペ窓の矩形（位置・大きさ）を誰が決めるか」だけであり、決まった矩形に対して
  画面をキャプチャしフィルタを適用する後段の処理は共通にできる。

## 代替案

1. **対象アプリ指定を完全に別の描画経路として実装する**（例: 対象ウィンドウ全体を
   別プロセス/別レンダラでキャプチャ・合成する）。却下: キャプチャ・シェーダ適用・
   uniform 同期のロジックを 2 系統保守することになり、sensus-core への一元化
   （`docs/adr/2026-05-31-sensus-core-consolidation.md`）で排除したはずの二重実装を
   別の層で再発させる。
2. **対象アプリ指定モードを持たず、手動ルーペのみに留める**。却下: 「見たいアプリを
   選ぶだけで体験できる」という UX 上の価値を捨てることになる。

## 根拠

- **経路の一本化**: ルーペ窓の矩形が「ユーザーがドラッグで決める」か「対象ウィンドウに
  自動追従して決まる」かの違いに矮小化できるなら、キャプチャ→シェーダ適用→
  描画という後段はモードによらず共通化できる。sensus-core 一元化と同じく、
  正本を 1 つに保つ設計判断の延長線にある。
- **既存のルーペ窓インフラを再利用できる**: 透過・最前面・クリックスルー・
  モード遷移（`LoupeWindowPolicy`）は #14 で実装済みで、そのまま対象アプリ指定
  モードの土台として使える。

## 結果・トレードオフ

- 対象アプリ指定モードの実装は「ルーペ窓の矩形を誰が決めるか」という差分に
  限定されるため、キャプチャ・シェーダ・uniform 経路の新規実装は不要になる見込み。
- **後続で詰める課題**（本 ADR の決定時点で未解決、後続設計に委ねる）:
  - 対象ウィンドウが他のウィンドウに隠れた場合、画面領域キャプチャでは手前の
    ウィンドウまで加工されてしまう。macOS は ScreenCaptureKit のウィンドウ単体
    キャプチャで回避できる見込み（#3）。
  - 追従の頻度: #5（60Hz uniform 同期）に、対象ウィンドウ矩形のポーリングを足す。
  - Android（#4）: 他アプリのウィンドウという概念がないため、全画面か手動ルーペ
    のみになる見込み。
  - 最小化・別 Space への移動・終了時の挙動: ルーペを隠すか、手動モードへ戻すかは
    未確定（→ 2026-09-28 追記で確定）。

## 追記（2026-09-28, #81）

追従対象は**ウィンドウ単位**（macOS では `CGWindowID`、X11 では Window ID
（XID）で識別する）とする。本 ADR「結果・トレードオフ」の「後続で詰める課題」と
していた項目のうち、次を確定する。選択 UI そのものの実装とウィンドウ追従の実装は
#91 に切り出し、#3 / #5 の後に着手する。

### 最小化・別 Space への移動・終了時の挙動

- 対象ウィンドウが最小化されるか、別 Space へ移動したら、ルーペ窓を隠す。
  **最小化と別 Space への移動は区別せず、どちらも同じ扱い（隠す）とする。**
  対象ウィンドウが元の状態（最小化解除・元の Space への復帰）に戻ったら、
  ルーペ窓を再表示する。
  - macOS: フルスクリーン Space に乗っているウィンドウ（`NSWindowCollectionBehavior
    .fullScreenAuxiliary` / `canJoinAllSpaces` が付いたウィンドウ）も「別 Space」
    として扱い、隠す対象に含める。
  - X11: `_NET_WM_DESKTOP`（現在のデスクトップ番号と不一致なら「別 Space」相当）と
    `_NET_WM_STATE_HIDDEN`（最小化相当）を監視して判定する。
- 対象の**ウィンドウ**が消えたら（ユーザーに閉じられた、またはプロセスが終了した）、
  手動モードへ自動的に戻し、ユーザーに通知する。通知手段は**アプリ内トースト、
  またはトレイ（#15）経由**のいずれかとする。

### OS ごとの提供可否

対象アプリ指定モードは、他アプリのウィンドウ一覧とその位置をクライアント側から取得でき、
かつルーペ窓をその座標へ自動配置し続けられる OS でのみ提供する。

| OS | 可否 | 根拠 |
|---|---|---|
| macOS | 提供する | `CGWindowListCopyWindowInfo`（CGWindowList）または ScreenCaptureKit の `SCShareableContent` で、他アプリのウィンドウ一覧・ジオメトリを取得できる。**`SCShareableContent` は画面収録権限が必須**（権限まわりは後述「必要な権限（macOS）」参照）。 |
| X11 (Linux) | 提供する | ルートウィンドウのプロパティ `_NET_CLIENT_LIST`（EWMH）でウィンドウ一覧を取得でき、個別ウィンドウのジオメトリも X11 プロトコルで取得できる（詳細は下記「X11 の実装メモ」）。 |
| Windows | ランナー作成時に確定 | `EnumWindows` でウィンドウ一覧、`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` でジオメトリ、`Windows.Graphics.Capture` でウィンドウ単体キャプチャが取得できる見込み。Windows ランナーは現状未作成（`README.md`「対応プラットフォーム」参照）のため、実装可否の最終確認はランナー作成時に行う。 |
| Wayland (Linux) | 提供しない | 標準プロトコルでは他ウィンドウの座標を取得できない（ウィンドウ一覧の取得自体もコンポジタ固有の拡張がある場合のみ可能で、標準では無い）。さらに、クライアントは自分のウィンドウの絶対位置すら指定できない（コンポジタが配置を決める設計）ため、ルーペ窓を対象ウィンドウの座標へ自動配置すること自体が成立しない。`xdg-desktop-portal` の ScreenCast でウィンドウ単体を選んで映像をミラー表示する方式も検討したが却下: 座標を取得できない以上、選んだ映像をルーペ窓の位置・大きさとして対象ウィンドウに一致させ続けることができず、「自動追従」という要件そのものを満たせない。 |
| Android | 提供しない | 一般的な権限では、他アプリのウィンドウ矩形を取得する公開 API がない。`AccessibilityService` なら取得できるが、目的外の利用は Play のポリシー上リスクが大きい。`MediaProjection` の単一アプリ共有（Android 14+）は、ユーザーがシステムダイアログで対象を選ぶ方式で、アプリ側から指定できず、矩形も返さない。 |

Wayland / Android では選択肢を UI 上で無効化し、理由を 1 行添える。

- Wayland: 「Wayland は他アプリのウィンドウ位置を取得できないため使用できません」
- Android: 「Android では他アプリのウィンドウ位置を取得できないため使用できません」

**要検証**: 上記は API の存在・用途についての公開情報ベースの整理であり、
flutter_rust_bridge 経由での実際の呼び出し可否や、macOS の CGWindowList 系 API の
将来的な非推奨化・置き換えの影響、X11 環境（ウィンドウマネージャ差）でのジオメトリ取得の
安定性は、#3 実装時に実機で確認する。座標系の扱い（`CGWindowList` は左上原点・
ポイント単位、`NSWindow` の座標系は左下原点）と、マルチディスプレイ環境での
表示倍率（DPR）の換算も未検証。

### X11 の実装メモ

- reparenting なウィンドウマネージャ（多くの WM が該当）では、ウィンドウ自身の
  座標がフレーム（装飾）内のオフセット座標になるため、スクリーン座標へは
  `XTranslateCoordinates` で変換する必要がある。
- 装飾込みの外形は `_NET_FRAME_EXTENTS`（EWMH 標準）または `_GTK_FRAME_EXTENTS`
  （GTK 系クライアントサイドデコレーション）で補正する。
- **XWayland の落とし穴**: XWayland 経由だと X11 接続自体は成立してしまうため、
  「X ディスプレイに接続できるかどうか」で X11/Wayland を判定してはいけない。
  モードの判定は `XDG_SESSION_TYPE` または `WAYLAND_DISPLAY` 環境変数で行う。

### 手前のウィンドウに隠れる問題への対処

- macOS: ScreenCaptureKit のウィンドウ単体キャプチャ（`SCContentFilter` を
  ウィンドウ単位で作る）で、対象ウィンドウの手前に他ウィンドウがあっても
  対象だけをキャプチャできる見込み（#3、本 ADR「結果・トレードオフ」参照）。
- X11: `XComposite` 拡張（`XCompositeRedirectWindow` + `XCompositeNameWindowPixmap`）
  でウィンドウ単体を独立した pixmap としてキャプチャできる可能性がある。
  **要検証**（#3 実装時に確認）。使えない場合の既知の制約: 画面領域キャプチャに
  フォールバックし、対象ウィンドウの手前に他ウィンドウが重なっている間はそちらも
  一緒にフィルタ加工されてしまう。

### 選択 UI

対象アプリを選ぶ UI は、アイコン付きのウィンドウ一覧（行ごとにアプリアイコンと
ウィンドウタイトルを表示するリスト）とする。実装は #91 に切り出す。選択 UI を
開く時点で必要な権限は「必要な権限（macOS）」を参照。**ウィンドウタイトルは
プライバシー情報になり得るため、選択 UI での表示のみに用い、ログや永続化には
残さない。**

### 必要な権限（macOS）

- **選択 UI と権限の関係**: 選択 UI を開く時点で画面収録の権限が必要（macOS
  10.15 以降、他アプリの `kCGWindowName` は権限がないと `nil` になる）。
  権限がない間は、アプリ名とアイコンだけの一覧（`CGWindowListCopyWindowInfo`
  は権限なしでも `bounds` と `owner`（アプリ名相当）を返す）に落とすか、
  先に権限の案内を出す。
- **権限フロー**:
  1. 初回は事前説明（なぜ画面収録の許可が要るか）を出してから
     `CGPreflightScreenCaptureAccess` で状態を確認し、`CGRequestScreenCaptureAccess`
     を呼んで OS の許可ダイアログを出す。
  2. 拒否された場合は、システム設定「プライバシーとセキュリティ > 画面収録」の
     URL へ案内する。
  3. 許可された後は、アプリの再起動を案内する（画面収録権限は再起動後に
     反映される仕様のため）。
  4. 実行中に権限が取り消された場合（`SCStream` の `didStopWithError`）は、
     手動モードまたはデモ画面へ戻す。
  5. macOS 15 で導入されたとされる定期的な再確認（許可の失効・再確認ダイアログ）の
     扱いは **要検証**。
  6. この画面収録権限は、対象アプリ指定モード専用ではなく、**手動モードの
     ライブキャプチャ（#3）でも必要になる**。
  7. **開発ビルドは ad-hoc 署名のため、TCC（Transparency, Consent, and Control）の
     許可がビルドのたびに外れやすい**。署名が変わると TCC は別アプリとみなし、
     権限を再度求め直す。開発中は許可し直しが必要になる前提で作業する。
