# ADR: プレビュー描画の診断ログを、リリースでも利用者の端末へ書く

- **決定日**: 2026-11-14（Issue #185）
- **記録日**: 2026-11-14
- **ステータス**: Accepted

## 文脈（問題）

実機で「フィルタの付け外しを繰り返していたらプレビューが固まった」という報告があった
（#185）。調べた範囲では、明るい画像に starbursts を掛けると CPU 描画が 1 回に数十秒かかり、
その間プレビューが変わらないことが最も有力な原因だったが、報告時の操作（どのフィルタを
重ねていたか）は後から確かめられなかった。

固まりは利用者の端末で、リリースビルドで起きる。デバッグ出力（`debugPrint`）や
`FlutterError.reportError` は、リリースでは利用者の目にも開発者の手元にも残らない。
次に起きたとき「どの段で・何を描いていて・何秒止まっていたか」を辿れる記録が要る。

一方で、利用者の端末にファイルを書くことには次の懸念がある。

- 個人情報: 読み込んだ画像のファイル名・パス、ホームディレクトリのユーザー名が混ざりうる
- 容量: 書き続けるとディスクを圧迫する
- 本体への影響: ログの失敗でアプリが止まってはいけない

## 決定

1. **リリースでも有効にする**。`main()` が起動時に、アプリのサポートディレクトリ
   （`path_provider` の `getApplicationSupportDirectory`）の `logs/preview-diagnostics.log` を
   書き込み先にする（実装は `lib/services/preview_diagnostics.dart`）。
   - Linux: `~/.local/share/com.example.universal_experience/logs/`
   - macOS（サンドボックス）: `~/Library/Containers/com.example.universalExperience/Data/Library/Application Support/com.example.universalExperience/logs/`
   - Windows: `%APPDATA%\com.example\universal_experience\logs\`
2. **書く出来事を絞る**。描画の失敗（`preview_failed`）、1 回の描画が 10 秒を越えて
   終わらないこと（`preview_stalled`）とその後の完了（`preview_recovered`）、描画の段取りの
   例外（`preview_error`）、起動（`app_start`）、原画比較の開始・解除（`bypass_on` /
   `bypass_off`）、ホットキー「押している間だけ原画」で原画比較が切り替わったときと keyUp（`hotkey_hold_original`。キーリピートの keyDown は書かない。長押しでログを埋めて肝心の記録を押し出さないため）。
   普段の描画（成功・10 秒以内）は書かない。
3. **個人情報を書かない**。書く値は、こちらで組み立てたもの（描画の段・フィルタの
   カタログ id・層の数・強度・サンプル id・寸法・経過ミリ秒・例外の**型名**）だけ。
   - ユーザー画像は `user` とだけ書く（ファイル名・パス・寸法の元になった画像の中身は書かない）
   - 例外の**メッセージは書かない**（パスやファイル名を含みうるため）。スタックも書かない
   - 万一の取りこぼしに備え、値は英数字と `_.+:-` だけに絞り、それ以外（パス区切り・空白・
     改行など）は `_` に置き換え、80 文字で切る
   - 端末の外へは送らない（送信の仕組みを持たない）。利用者が自分で開いて、Issue に貼るかどうかを決める
4. **容量の上限**。1 ファイル 256 KiB を越えたら `.1` へ退避して新しく始める（最大 2 ファイル、
   約 512 KiB）。1 行は百数十バイトなので、数千件ぶん。
5. **失敗は握りつぶす**。ディレクトリが作れない・書けないときは、ログなしで続ける。
   書き込みは順番に 1 つずつ、描画の経路を待たせない。
6. **無効にできる**。環境変数 `UE_PREVIEW_DIAGNOSTICS=0` で起動すると、書き込み先を作らず何も書かない。
   テスト（`flutter test`）は `main()` を通らないので、何も書かない。

## 却下した案

- **デバッグビルドだけで有効にする**: 固まりは利用者のリリースビルドで起きるので、肝心のときに残らない。
- **例外のメッセージを、ホームディレクトリを `~` に置き換えて書く**（最初の実装）:
  ホームの外のパス（外付けディスク `/mnt/…`、Windows の別ドライブ）や、`HOME` が `/` のときの
  全置換など、置き換えで防ぎきれない。型名だけにした。
- **クラッシュ報告サービスへ送る**: 送信の同意・依存の追加が要り、オフラインの前提（画像を
  端末の外に送らない）とも合わない。

## 影響

- 利用者は、固まったときに上のファイルを開けば、どの段で止まっていたかを確かめられる
  （README の「診断ログ」）。
- 書く出来事・値を足すときは、この ADR の 3 の範囲（こちらで組み立てた値だけ）に収める。
  自由な文字列（例外のメッセージ・ファイル名）は足さない。
