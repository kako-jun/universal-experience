# ADR: 主画面を「統合一覧 + 3 カラム（広幅）/ 縦積み（狭幅）」にする

- **決定日**: 2026-09-30（Issue #72 のフェーズ B。PR #100）
- **記録日**: 2026-09-30（ADR 化）
- **ステータス**: Accepted（狭幅の一覧は暫定。「結果・トレードオフ」参照）

## 文脈（問題）

主画面は、色覚 7 型を選ぶ欄、advanced（sensus カタログ）30 フィルタを選ぶ欄、体験プリセット、
起動モード（設定窓/ルーペ窓・最前面・クリックスルー・ホットキー）が縦に積み上がった 1 本のスクロール画面
だった。次の問題があった。

- 「見え方を選ぶ」入口が色覚と advanced で分かれており、利用者は先に「どちらの欄か」を知っていなければ
  ならない。検索もできない。
- 選ぶ場所・プレビュー・調整（強度・パラメータ・受診喚起）が縦に離れ、選んだ結果を見るたびにスクロール
  が要る。
- 起動モードの設定が主役（見え方の比較）と同じ面積を取っていた。
- 色・余白・角丸・タップ領域の規約が無く、画面ごとにばらついていた（DESIGN.md で成文化）。

## 決定

1. **色覚 7 型と advanced 30 フィルタ（と体験プリセット 4 件）を 1 つの一覧（33 行 + プリセット）に統合する。**
   日本語名・英語名・かな/カナのインクリメンタル検索と、カテゴリ絞り込みを付ける。ロジックは
   `lib/services/filter_list_selection.dart`（純粋関数）に置き、書き込みは既存の入口
   （`selectColorVision` / `VisionFilterState.select` / `selectPreset`）のまま。
   `VisionFilterState` が唯一の正本であることは変えない。
2. **広幅（≥ 1000dp）は 3 カラム「選ぶ（左）/ 見る（中央）/ 調整（右）」、狭幅は縦積み**
   （プレビュー → 調整 → 選択）。1 画面で「選ぶ → 調整 → 見る」が完結することを目標にする。
3. **起動モード・最前面・クリックスルー・ホットキー一覧は AppBar のダイアログへ移す。**
   クリックスルー ON の間だけ、復帰方法を主画面最上部の `ClickThroughRecoveryBanner` に常時出す（#63）。
   ダイアログ内でスイッチを ON にしたときはダイアログを自動で閉じ、開いたままの間もダイアログ内で
   `Esc` を解除として効かせる。
4. **カテゴリ切替は `ChoiceChip` の `Wrap`**（「すべて」+ 7 カテゴリ、選択中はチェックと色）とし、
   一覧のスクロール領域の先頭に置く（低い画面で一覧を潰さないため）。
5. **ハイコントラストを第一級のテーマにする。** ライト/ダークと同じシードから `contrastLevel: 1.0` で
   生成し、`MediaQuery.highContrast` が報告される環境では自動で選ぶ。色は `colorScheme` のロールだけを使い、
   色だけで意味を伝えない。操作領域は 48dp 以上（`materialTapTargetSize: padded`）。

## 代替案

- **カテゴリ切替を `NavigationRail` にする**: 意味的には正しい（大分類のナビゲーション）が、広幅の左カラム幅は
  280〜340dp と狭く、Rail（最小 72〜80dp）を置くと一覧の行の幅が足りなくなる。プリセット・色覚・advanced の
  名前（特に英語）が折り返す。チップの `Wrap` なら 1 列の幅を保てる。
- **狭幅の選択を `NavigationBar` + ボトムシートにする**: 狭幅の理想形だが、選択・検索・キーボード操作・
  フォーカス管理をボトムシート前提でもう 1 組作る必要があり、#72 のスコープを超える。まず縦積みの最下段に
  固定高の一覧を置く形で出し、置き換えは別 Issue とする（暫定）。
- **色覚と advanced の 2 つの欄を残し、検索だけ足す**: 入口が 2 つのままで「どちらの欄か」を知る必要が
  残る。すべてを 1 つの一覧に並べて検索できる方が、症状名から探す当事者・家族の使い方に合う。
- **起動モードを主画面に残す**: 見え方の比較という主役の面積を削る。ルーペ窓へ移行後は主画面を見続ける
  ことが少なく、復帰方法だけを常時出せば足りる。
- **ハイコントラストを別実装（専用ウィジェット）にする**: 生成経路が二重になり保守できない。
  `ColorScheme.fromSeed` の `contrastLevel` だけを変える。

## 根拠

- この製品は色覚などのシミュレータで、当事者・家族が使う。入口を 1 つにして検索できること、色に頼らない
  表現（チェック・文言・形）、十分なタップ領域、ハイコントラスト対応は「見た目の好み」ではなく品質要件。
- 状態の正本を増やさない（`VisionFilterState` のみ）ので、統合しても sensus 連携・エクスポート・トレイの
  挙動は変わらない。一覧は純粋関数でテストできる。
- チップの `Wrap` は左カラムの幅制約の中で全カテゴリを常時見せられ、検索と併用できる。

## 結果・トレードオフ

- 狭幅の一覧は暫定で、一覧で選んだ直後は調整結果が画面の上側に移って見えなくなる。`NavigationBar` +
  ボトムシートへの置き換えまでの既知の状態（DESIGN.md §6.1）。
- Linux など `MediaQuery.highContrast` が報告されない環境では、OS の設定が有効でもハイコントラストへは
  自動で切り替わらない（手動切替は未実装）。
- advanced の各フィルタには説明文が無く、右カラムに出るのは名前とカテゴリだけ。
- ちょうど 1000dp の広幅では中央カラムが 420dp を下回り、Before / After は縦積みに切り替わる。
- 規約（色・余白・角丸・タップ領域・キー割り当て）は `DESIGN.md` が正本、実装の構造は
  `docs/ARCHITECTURE.md` が正本。
